## 1. Objective

Choosing the colour of a responsibility (担当領域) must be a visual act, not a HEX string that a manager has to type
correctly. The correction keeps the V1.6.2 contract intact: schema **7**, no migration, `Color_Hex` as the only stored
value, `Responsibilities.normalizeColor` as the only validation, one authorized snapshot for reads and no new write
path.

## 2. Confirmed root cause

`ManagerWebClient` rendered every responsibility field through the generic `field()` helper, so `color` was an
`<input type="text">` bound to `Color_Hex`. `responsibility` was the only record type whose value a manager can only
learn from a spec (`#RRGGBB`), and the form gave no feedback about the value — no swatch, no preview and no
browser-side hint before the server refused an invalid string.

## 3. Before behavior

| Scenario | V1.6.2 result |
| --- | --- |
| Create an area | Type `#357C9B` from memory, or leave it blank and hope for a default |
| Pick one of the documented palette colours | Type the exact code; the palette was not offered anywhere in the form |
| Custom colour | Type the exact code; no colour picker |
| Invalid value (`red`, `#12345`) | Accepted by the field, refused only after a save round trip |
| Preview the card colour | None; the manager had to save and look at the list |
| Selection state | None; there is nothing to select |

## 4. Corrected behavior

- **Twelve muted presets** (`Responsibilities.PALETTE`, extended from eight to twelve) are rendered as clickable
  swatches. The list is published to the client as `references.colors` and the client keeps an identical constant, so
  a swatch and the server default can never drift; `tests/v1_6_2-color-picker.test.js` asserts the equality.
- **Selection state is explicit**: `aria-pressed` on each swatch plus a check mark (`aria-hidden`, so it is decoration,
  not text) and a bordered selected state. Selection is never conveyed by colour alone.
- **Keyboard operation**: ArrowLeft/ArrowRight move the selection and the focus, Home/End jump to the first/last
  preset, and any other key is ignored. Each swatch is a real `<button type="button">` with the HEX value as its
  accessible name.
- **Custom colour** uses the browser's native `<input type="color">`, so no new dependency and no runtime colour maths.
- **HEX editing stays available** as an optional advanced control inside a collapsed `<details>` block; it is never
  required and never the default interface.
- **Live preview**: a preview card mirrors the name field and the selected colour (left border, dot and the stored
  `#RRGGBB` text) as the manager types.
- **Deterministic default**: a new area shows the first preset no known area uses yet, which is the same rule as
  `Responsibilities.nextColor()`. No responsibility name is hardcoded anywhere.
- **Validation is unchanged and server-side**: `Responsibilities.normalizeColor` still refuses anything but
  `#RRGGBB`, both through `Ui.saveResponsibility` and through the `responsibilitySave` web action. The client refuses
  an invalid HEX value before submit as a convenience only, and an invalid value never replaces the selection.
- **An edit stays a partial patch**: opening the form does not write `Color_Hex`, so an untouched colour is absent
  from the payload and a legacy blank value stays blank. Existing colours are preserved.
- **Consistency**: the area card, the area filter chip, the responsibility list, the project card and the task area
  chip all use the same display colour (`Responsibilities.colorOf`).

## 8. Security implications

- No new entrypoint, no new action and no new Script Property. `managerWebWrite('responsibilitySave')` is unchanged.
- `Color_Hex` continues to be validated by `Responsibilities.normalizeColor` inside `validate()` for create, update,
  retire and reactivate; the browser value is data, never authority.
- Only validated `#RRGGBB` strings are used in `style` attributes; the client normalizes with `/^#[0-9A-F]{6}$/`
  before writing them, and stored text is still rendered with `textContent`/DOM creation (`npm run validate` rejects
  markup insertion).
- `references.colors` publishes palette constants only — no identifiers, names or personal data.

## 9. Performance implications

One static list of twelve strings on the existing `references` payload; the picker renders from the cached snapshot, so
opening the form performs no additional read. No extra write, no extra cache entry and no per-click RPC.

## 10. Known limitations

- The native `input type="color"` UI differs per browser and could not be verified here; the local tests use the Node
  DOM shim and mocks only.
- Contrast of a chosen colour against white text is not evaluated; the stored HEX is always shown as text next to the
  swatch, so colour is never the only signal.
- Legacy rows with a blank `Color_Hex` keep the value blank until a manager deliberately picks a colour.
- Browser paint, zoom and screen-reader behaviour remain manual Workspace checks.
