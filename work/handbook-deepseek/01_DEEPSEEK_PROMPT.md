# DeepSeek への制作依頼（全文を貼り付け）

あなたは、日本の製造業・設計部門向け業務ソフトの研修教材を制作するテクニカルライター兼エディトリアルデザイナーです。

添付の日本語原稿、制作仕様、実画面 PNG を使い、**「設計・開発課 管理」のメンバー用・マネージャー用操作マニュアル**を制作してください。システム管理者（ADMIN）用マニュアルは不要です。

## 到達目標

- メンバーは、最初に自分の担当・期限を確認し、作業内容を開き、完了報告または納期変更申請を正しく行える。
- マネージャーは、既存案件の状況を確認し、必要な案件・作業を登録して担当者を設定し、申請に判断を返せる。
- 画面ごとの全機能説明から始めず、利用者が達成したい仕事の順に教える。

## 入力資料と信頼順位

1. `03_AUTHORING_SPEC.md` の確認済み事実・制約・既知の不一致。
2. `02_HANDBOOK_JA.md` の手順原稿。
3. 添付 PNG の実際のボタン名・位置。

画像は現行ローカル UI＋架空データです。本番確認済みと書かないでください。古いマニュアルや一般的なタスク管理ソフトの知識で機能を補完しないでください。

UI と原稿が一致しない場合は、操作やボタンを創作せず、「配布前確認事項」に記録してください。原稿に示した既知の不一致は勝手に整合させないでください。

## 出力物

1. `MEMBER_QUICKSTART_JA.md`：A4 2ページを目安。
2. `MANAGER_QUICKSTART_JA.md`：A4 2ページを目安。
3. `HANDBOOK_JA.md`：共通・メンバー・マネージャー・困ったときの4部構成。約20〜28ページ。
4. `REVIEW_CHECKLIST_JA.md`：未撮影、未確認、表記不一致、配布前確認事項。利用者向け本文と分ける。
5. PDF を生成できる場合は同名 PDF も出力。生成できない場合、印刷用 Markdown と CSS を出し、PDF を作成したと偽らない。

最初に簡潔な目次を示し、そのまま完成原稿まで作成してください。提案だけで終了しないでください。

## 執筆ルール

- 全文を自然で簡潔な日本語にする。
- 製品名は必ず「設計・開発課 管理」。
- 役割名は「メンバー（MEMBER）」「マネージャー（MANAGER）」。
- ボタン名は画面に見える日本語を「」で囲み、勝手に言い換えない。
- 「右のボタン」だけでなく「対象タスクの『完了報告』」のように対象を明示する。
- 1手順は1操作。通常3〜6ステップで区切る。
- 各手順に「目的」「開始画面」「事前条件」「操作」「完了の見分け方」「次の行動」を付ける。
- 必須入力と、よい運用のための推奨入力を区別する。
- 練習例は架空データと明記。本番環境に練習用レコードを作らせない。
- SQL、API、スキーマ、移行、サーバー設定、環境変数、開発者向け説明は利用者本文に入れない。
- メンバーに既存レコードの編集、直接完了、削除、承認を案内しない。
- マネージャーに ADMIN 専用操作を案内しない。必要な場面は「運用担当者に相談」で終える。
- メールが必ず届く、入力が自動保存される、申請すると期限がすぐ変わる、等の保証を書かない。
- 「受付完了」「承認待ち」「完了」の違いを繰り返し明確にする。

## 画像とページデザイン

- 添付の実 UI 画像を使う。AI で画面やボタンを描き直さない。
- MANAGER の説明には MANAGER 画像、MEMBER の説明には MEMBER 画像を使う。
- 画像の文字を修正して存在しないラベルにしない。
- 1画像に番号①〜⑤を最大5個。本文の同じ番号と一致させる。
- 番号や矢印は対象の横に置き、文字やボタンを隠さない。
- 細部は拡大トリミングする。長いページ全体を小さく縮めない。
- 画像加工できない場合は、未注釈画像＋直下の「クリック位置一覧」で代替する。注釈済みと主張しない。
- 画像のない手順には明確な「要撮影」制作メモを残す。別画面を代用品として載せない。
- A4縦、余白15〜18mm、日本語本文10.5〜11.5ptを目安。
- 1ページに1つの目的。画像と対応手順を同じページ、または連続した見開きに置く。
- 図のキャプションに図番号・役割・目的を付ける。
- フッターに版／日付／ページ番号。見出しだけがページ末に残らないようにする。
- クイックスタートは、初日から必要な操作だけに絞る。全画面の説明を詰め込まない。

## 重要な事実

- メンバーは新規プロジェクト・サブプロジェクト・自分のタスクを作成できる。ただし作成後の通常編集はマネージャーに依頼する。
- 完了報告は、閲覧可能で条件を満たす作業について提出できる。担当者でないと絶対に報告できない、と書かない。
- 納期変更申請は、担当しているメンバーの作業が対象。
- メンバーの完了報告は承認前には完了ではない。
- マネージャーには申請判断と、条件を満たすタスクの「完了にする」という直接判断の別ルートがある。
- タイムラインの表示期間変更は、作業の期限変更ではない。
- 現行フォームは開始日・終了日を扱う。旧版の「所要期間から開始日を導く」説明を持ち込まない。
- 完了メモは画面に「任意」とあっても現在のフォームは空欄を拒否する。必ず内容を書く手順にし、表記矛盾をレビューリストに残す。
- 送信中に閉じる操作は送信取消ではない。送信結果不明では、確認せずに新しい申請を繰り返さない。

添付資料を読み、指定の4成果物を作成してください。
